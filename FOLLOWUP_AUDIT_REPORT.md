# Follow-Up Audit Report

## Summary
Out of the 10 targeted items, 5 are **CONFIRMED WORKING** strictly as designed (including the reviewer bound, traceability wiring, and tool rule selection). However, 5 are identified as **GAPs**, including the lack of explicit image-to-entity mapping, blocking synchronous file operations inside the async API, and missing file size/type validation that poses a security risk.

## Item-by-Item Findings

### 1. `previous_qa` wiring (initial_analysis / re_analyze loop)
- **Status:** CONFIRMED WORKING
- **Evidence:** `backend/app/graph/nodes/update_state.py` (Line 26) & `backend/app/prompts/re_analyzer.py` (Line 20)
- **Explanation:** `update_state` actively appends incoming answers to the persistent `answers` array in the agent's state, accumulating them across all rounds. The `RE_ANALYZER_PROMPT` then correctly receives this entire cumulative history under the `{answers}` placeholder, ensuring previously answered questions are not lost or re-asked.
- **Impact if GAP:** N/A

### 2. `source_traceability` wiring (generated prompts)
- **Status:** CONFIRMED WORKING
- **Evidence:** `backend/app/graph/nodes/generate_scenes_and_prompts.py` (Lines 26-59, 170-175)
- **Explanation:** A dedicated helper `_collect_entity_sources` safely extracts the `source` tags from the `VideoSpecification` entities associated with the scene (character, location, product IDs). This result is actively assigned to the `source_traceability` list on each `GeneratedPrompt` object.
- **Impact if GAP:** N/A

### 3. Reference-image-to-entity mapping
- **Status:** GAP FOUND
- **Evidence:** `backend/app/graph/nodes/analyze_script.py` (Lines 29-32) & `backend/app/prompts/initial_analysis.py` (Line 14)
- **Explanation:** The backend simply flattens all uploaded character, product, and brand images into a single `all_image_urls` array and passes them as raw base64 blocks to the Claude Vision endpoint. There is no explicit mapping mechanism associating a specific image with a specific entity ID.
- **Impact if GAP:** The system relies entirely on the LLM to guess which image corresponds to which script character/product based purely on visual deduction, which can lead to crossed assignments or hallucinated character traits.

### 4. Precedence model enforcement (USER > SCRIPT > INFERENCE > DEFAULT)
- **Status:** CONFIRMED WORKING (Not enforced in code, relies entirely on prompt compliance)
- **Evidence:** `backend/app/graph/nodes/build_video_spec.py`
- **Explanation:** There is no programmatic Python-side validation or conflict resolution comparing the final spec's `source` tags against the user's answers. The system delegates this precedence hierarchy entirely to the LLM via the instructions in `VIDEO_SPECIFICATION_PROMPT`.
- **Impact if GAP:** N/A

### 5. Canonical entity ID consistency across pipeline stages
- **Status:** CONFIRMED WORKING
- **Evidence:** `backend/app/validators/prompt_reviewer.py` (Lines 185-199)
- **Explanation:** The Prompt Reviewer Agent has a strict deterministic check (Category A3: Entity ID validation). It explicitly validates that every `location_id` and `character_ids` generated by the LLM in the scene plan exists in the canonical lists (`self._location_ids` and `self._character_ids`) from the spec, flagging any invented IDs as `BLOCKER`s.
- **Impact if GAP:** N/A

### 6. Tool-specific prompt behavior actually varies
- **Status:** CONFIRMED WORKING
- **Evidence:** `frontend/src/app/page.tsx` (Line 116) & `backend/app/graph/nodes/generate_scenes_and_prompts.py` (Line 77-84)
- **Explanation:** Unlike output requirements, the tool selection *is* correctly wired. The frontend UI captures it via `VideoToolSelector`, it is sent as form data, stored in `state["selected_tool"]`, and successfully retrieves specific rules via `get_tool_rules(tool)` before being passed to `GENERATION_PROMPT`.
- **Impact if GAP:** N/A

### 7. Concurrency / blocking calls 
- **Status:** GAP FOUND
- **Evidence:** `backend/app/parsers/pdf_parser.py` (Lines 27, 42) & `backend/app/parsers/text_parser.py` (Line 5)
- **Explanation:** While the Cloudinary upload is safely wrapped in `run_in_threadpool`, the file parsers are not. `pdfplumber.open(file_path)` and `pdfium.PdfDocument(file_path)` execute synchronously inside the `async def parse()` function, which will heavily block the FastAPI event loop when processing large PDFs.
- **Impact if GAP:** A single user uploading a large or complex PDF will freeze the backend, causing timeouts or degraded performance for all other concurrent users.

### 8. Security basics
- **Status:** GAP FOUND
- **Evidence:** `backend/app/api/routes/scripts.py` (Lines 117-124, 150-159)
- **Explanation:** The endpoint validates file extensions (only `.txt` or `.pdf` for scripts) but lacks any file size limit checks before `await file.read()`. Furthermore, there is zero type or size validation for the `character_images`, `product_images`, and `brand_images` arrays before passing them to Cloudinary.
- **Impact if GAP:** Users can upload massive 10GB payloads or malicious non-image files, leading to out-of-memory (OOM) crashes on the server or bloated cloud storage costs.

### 9. Review Agent correction chain — actual bound confirmation
- **Status:** CONFIRMED WORKING
- **Evidence:** `backend/app/validators/prompt_corrector.py` (Lines 27, 228-236, 259)
- **Explanation:** The fallback chain enforces a strict hard cap via the `MAX_LLM_PATCH_CALLS = 6` constant. The code explicitly checks `if llm_calls_used >= MAX_LLM_PATCH_CALLS:` and falls through safely to the deterministic `_safe_simplify` method (e.g., stripping text without an LLM) if the cap is reached, guaranteeing bounded execution.
- **Impact if GAP:** N/A

### 10. Dead/leftover code from superseded designs
- **Status:** GAP FOUND (Design implementation drift confirmed)
- **Evidence:** `backend/app/schemas/generated_prompt.py` and `backend/app/graph/nodes/generate_scenes_and_prompts.py`
- **Explanation:** There are absolutely no references to `spacy` or `en_core_web_sm` remaining in the backend. However, it is confirmed that the system relies exclusively on the **one-prompt-per-shot** architecture. The `PromptSet` is generated by iterating over `shots` to yield a single `GeneratedPrompt` per shot. Clip-based grouping (one prompt per scene) was never actually implemented in this codebase.
- **Impact if GAP:** N/A (Just confirming the current architectural state).
